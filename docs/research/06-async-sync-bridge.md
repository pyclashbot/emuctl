# 06 — Async core + sync wrapper: prior art, tooling, hazards

Topic: how real libraries ship and maintain an async core with a sync convenience API; anyio blocking portals; deadlock/executor/cancellation hazards; testing both surfaces; Windows subprocess/loop gotchas. Informs DESIGN.md locked decision #1 ("Async core + sync wrapper", sync bridge = highest-risk layer + prime test target) and deferred item #2 (bridge design: anyio vs asyncio-native, sync wrapper semantics and cancellation).

## 1. Question

- What prior art exists for async-core + sync-wrapper libraries, and which bridging strategies have successful SDKs settled on (hand-maintained twins; sync-wraps-async portals; async-wraps-sync via to_thread)?
- How do anyio blocking portals (`start_blocking_portal`, `BlockingPortalProvider`, `from_thread.run`) let one coroutine run under a sync facade, and how mature is that in 2026? What do fastmcp/httpx/textual do?
- What are the deadlock/executor hazards (calling sync wrapper from inside a running loop, executor sizing, cancellation crossing the bridge, context managers spanning sync/async)?
- How do you test both surfaces cheaply (pytest-asyncio, anyio pytest plugin)?
- Windows: ProactorEventLoop vs SelectorEventLoop implications for `asyncio.create_subprocess_exec` (adb/memuc subprocesses), and other subprocess/asyncio gotchas.

## 2. Findings

### Strategy taxonomy — how the wild does it

There are exactly four viable strategies; successful projects rarely mix them:

1. **Hand-maintained sync/async twin APIs.** The sync and async clients are two parallel implementations (often sharing a sans-I/O or config/validation core, but with two method bodies per operation). This is what httpx, openai-python, anthropic-sdk-python, and redis-py do. [1][2][3]
2. **Sync built from async via a portal / dedicated background event loop.** AnyIO's `start_blocking_portal()` runs an event loop in a background thread and exposes `portal.call(coro_fn, *args)`; `BlockingPortalProvider` gives a shared, lazily-started portal for repeated sync calls; `wrap_async_context_manager()` converts `async with` to `with`. This is the standard "wrap my async API for sync users" tool. [4]
3. **Async built from sync via `asyncio.to_thread` / `anyio.to_thread.run_sync`.** The inverse direction (sync core, async sugar, or offloading blocking calls inside an async app). fastmcp does this for *sync tool functions* — it runs user's sync tool code via `anyio.to_thread.run_sync` so it doesn't block the server's event loop, which is the correct direction for a plugin/tool surface. [5] Not applicable to emuctl's wrapper direction (our core is async), but critically relevant inside the async core whenever it *must* call something blocking.
4. **Source transformation: `unasync`.** Write the async version, compile-time transform it into the sync version (`await` → non-await, `async def` → `def`). Maintained by python-trio, the approach was proposed in urllib3 #1323; it keeps both surfaces in lockstep with zero runtime dependency. [6] Real but niche; check-in generated code is the usual practice. Used where API surface is large and "twins drifting" is intolerable.

**Which do successful SDKs settle on?** Large SDKs with big teams (httpx, openai, anthropic, redis-py) converge on strategy 1 (hand-maintained twins), accepting the duplication because they need per-surface tuning and their tooling (type checking, generated surface) makes duplication manageable — and because a portal wrapper imposes a background-thread loop on every user, which is unacceptable in a ubiquitous HTTP client. [1][2][3] Libraries that are *primarily* async but want a sync convenience inlet (playwright-python, fastmcp's server runner, anyio-based apps) converge on strategy 2. [7][5][4]

### Concrete prior-art notes

- **httpx**: `Client` (sync) and `AsyncClient` share a `BaseClient` but every I/O method is implemented twice; maintainers discussed whether the clients were "90% the same code" and still chose explicit duplication for clarity and to keep each surface independently testable. [1]
- **openai-python (and the same-template anthropic SDK)**: "providers convenient access... offers both synchronous and asynchronous clients powered by HTTPX" — `SyncHttpxClientWrapper`/`AsyncHttpxClientWrapper` — i.e., twins, not a wrapper bridge. The public codegen'd resource classes are also duplicated (`resources/` vs `resources/_async/`? — flag: structure inferred from DeepWiki/PyPI, verify at implementation time). [2]
- **redis-py**: shipped asyncio support *inside* the same package (`redis.asyncio`) as hand-maintained twins, making the third-party `aredis` obsolete (flag: historical claim, moderately confident — check release notes). [10]
- **playwright-python**: sync API is *generated* (`sync_api/_generated`) as a greenlet-based overlay on the async core — the sync driver context-switches between user sync code and the library's event loop using greenlets, giving true blocking semantics without threads. Works, but a C-extension dependency (greenlet) and bespoke machinery; notable that even Microsoft chose codegen over hand-writing. [7]
- **fastmcp**: async-native server; `run()` is documented as "a synchronous wrapper around the async server implementation"; user-defined sync functions (tools) are offloaded with `anyio.to_thread.run_sync` (contextvars-safe per their docs). [5]
- **httpx transport internals** additionally use **sniffio** to detect whether code is running under asyncio or trio — relevant if emuctl ever wants loop-agnostic internals; sniffio is the accepted detector for "what async world am I in." (flag: general knowledge; cite sniffio docs at implementation time) [11]
- **aiosqlite**: a different but instructive direction — async API over a sync stdlib (`sqlite3`) implementation by running *one dedicated background thread per connection* and hopping requests over a queue. Directly relevant to emuctl because our sync wrapper is the mirror image: a dedicated background loop per client works, but costs a thread-hop per call (~20–60 µs overhead measured for sqlite on 3.14 — irrelevant magnitude for emulator subprocess calls which cost milliseconds–seconds; the concern is never per-call overhead, it's loop-ownership semantics). [8]
- **boto3/aioboto3**: flag (hearsay, moderate confidence): aioboto3 historically re-patches botocore's sync client machinery into awaitable wrappers — an example of strategy 3 done *inside* the client, and a well-known source of fragility between boto versions. Avoid this shape. Confirm with aioboto3 repo when relevant.
- **asyncer (tiangolo)**: purpose-built library for this exact problem: `syncify` (wrap an async fn for sync callers) and `runnify`/`asyncify` built *on anyio*. Small adoption but the clearest "official-adjacent" reference for the wrapping patterns. (flag: verify API names against current docs) [9]

### anyio blocking portals: mechanics and maturity

From the official docs (AnyIO 4.15.x, the stable current line) [4]:

- `start_blocking_portal()` enters a context manager that starts an event loop (asyncio by default; `backend=` accepts '"trio"' and anyio runs the *same coroutine* under either) **in a dedicated thread**, exposed through the **blocking portal** façade: `portal.call(coro_fn, *args)` schedules the coroutine and blocks the calling thread until completion, re-raising exceptions.
- `BlockingPortalProvider` is explicitly documented *"if you're building a synchronous API that needs to start a blocking portal on demand"* — i.e., it is the designed tool for exactly emuctl's wrapper layer: multiple threads share one portal; the portal's own task group supports spawning tasks and wrapping async context managers.
- `portal.start_task_soon()` returns a `concurrent.futures.Future`; cancelling that future cancels the task inside the loop — this is the one bridge point where sync-side cancellation translates meaningfully to async.
- `to_thread.run_sync(..., abandon_on_cancel=True)` semantics: awaiting task can be cancelled but **the worker thread keeps running** — the outcome is abandoned, not the work. This is the core truth of cancellation across the bridge: *threads cannot be cancelled in Python*; you can only stop caring. [4]
- `from_thread.check_cancelled()` exists so long-running sync code inside an async-launched worker thread can voluntarily observe cancellation — the mirror-image need *inside* a sync wrapper is `asyncio.get_running_loop()` detection (below). [4]
- Maturity: anyio 4.x is the de-facto standard abstraction layer (used by httpx/httpcore, fastmcp, and effectively the whole HTTPX/Starlette ecosystem via anyio as a transitive dep on >40M/month basis — flag: no fresh citation pulled; it's uncontroversial and checkable). AnyIO 4.15.1 is the documented current version, docs current as of retrieval. [4]

**Nesting deadlock: the classic failure.** `asyncio.run()` raises `RuntimeError: asyncio.run() cannot be called from a running event loop` and, crucially, so does *loop.run_until_complete* when a loop is already running in the thread — the single most common way sync-wrapping libraries fail in user code: called from inside another framework's event loop (Jupyter is the canonical victim). [15] A wrapper must **detect a running loop** and either raise a clear error or use a portal (which works from a *different thread* even while the calling thread loops fine — the blocking is in the calling thread, the loop is elsewhere, so no deadlock). This is precisely what `start_blocking_portal` provides for free. AnyIO documents portals under "Accessing the event loop from a foreign thread" [4]; anyio discussions confirm portals are the designed answer for external threads talking to a loop [12].

### Cancellation, context managers, and hazards

- **Cancellation cannot cross the thread boundary for real.** Any a future returned by an executor or a portal *waiting* on a thread-backed operation can only abandon, not abort. For emuctl that's fine: our operations are subprocess-driven and idempotent-ish (screenshots bounded by total buffer write, clicks short); document that sync-side `KeyboardInterrupt`/`.cancel()` leaves the work running to completion. The AnyIO `Future` cancellation *does* cancel the *portal-scheduled coroutine* in the loop — meaning under a portal wrapper, cancellation semantics are actually *reasonable* for the async part, unlike raw `to_thread`. [4]
- **Shutdown/lifecycle asymmetry:** pymemuc/py-clash-bot's `__del__`-based cleanup already demonstrated destructors as a failure surface (NOTES.md §5). A sync wrapper must not tear down its portal inside `__del__`; it should require context-manager or explicit `close()` and tolerate `__del__` no-op. Control: make cleanup idempotent and never pick up locks in finalizers (informal; consistent with NOTES.md inherited principles).
- **Context managers across the bridge** are solved: `portal.wrap_async_context_manager()` turns `async with` into `with` and holds the `__aexit__` open until the sync block exits — this is exactly the shape emuctl's `session()` / `emulator()` lifecycle needs on the sync side. Note the doc caveat: wrapped managers cannot be used inside the *loop's own* sync callbacks (irrelevant for emuctl's user-facing surface). [4]

### Executor sizing and loop configuration

- AnyIO's default worker-thread limiter is **40** (`to_thread.current_default_thread_limiter().total_tokens = 60` shown as adjustment); asyncio's own default thread pool max is `min(32, os.cpu_count() + 4)` since 3.8. For emuctl, thread sizing is irrelevant *inside* async core (we mostly await subprocesses, not thread-blocking work). The only place thread sizing matters: (a) if the async core ever calls `to_thread` for blocking vendor CLI process-waits, and (b) sync wrapper sharing one thread for the portal — 1 thread is fine and *correct*, since the loop is event-driven, not thread-pool-driven. (docs-based: AnyIO source, asyncio ThreadPoolExecutor max_workers docs — flag: asyncio value from general knowledge, verify at implementation). [4][16]
- **Bounded waits everywhere** (via anyio `move_on_after` / `asyncio.wait_for`) are an emuctl-house principle (NOTES.md) and they drop trivially across the portal: portal.call propagates the exception the bounded wait raises, which becomes an ordinary sync-side exception.

### Testing the bridge

- **anyio ships a pytest plugin**: `anyio_backend` fixture parametrizes asyncio/trio backends; coroutine tests run under it. Officially documented with an important caveat documented *in their own testing docs*: pytest-asyncio's default `asyncio_mode=auto` can interact badly with anyio's plugin; the remedy given is pytest-asyncio strict mode or avoiding double plugin application. [17] Anyio docs (testing section) are current and describe this interaction explicitly (they recommend removing `asyncio_mode=auto` from config if both plugins are installed) [17].
- **Pragmatic split that works for emuctl-shaped code (moderate-confidence synthesis):**
  1. Contract-test the **async core** once, parametrized mostly asyncio-only (emuctl's real backend.) Trio support is free with anyio *if* the core is written backend-neutral; that is a design choice we must make consciously: **asyncio-native** core = simpler, `asyncio.create_subprocess_exec` first-class; **anyio core** = trio compat for free, at the price of an anyio dep and anyio's own subprocess layer for Windows.
  2. Test the **sync wrapper** as a distinct surface: every pair `X / await X` runs under one parametrized test (`async def test_x()` + `def test_x_sync()` both calling shared assertions) so barriers drift fail loudly. The bridge (portal creation, portal reuse, exception propagation, cancellation, context manager enter/exit) is *the* thing to test directly — including **pytest-style "called from an async test that wraps the sync wrapper"** negative test asserting the designed RuntimeError.
  3. Hypothesis stateful is overkill for the bridge; targeted pytest coverage of portal semantics (exception re-raise, backpressure of one shared portal, concurrent sync calls from 2+ threads) catches the real failure classes without property-based overhead (synthesis; flag as recommendation, not citation).

### Windows: subprocess on asyncio — the biggest emuctl-specific hazard

- **On Windows, asyncio has two loops: ProactorEventLoop (default since 3.8) and SelectorEventLoop, and `asyncio.create_subprocess_exec` *only* works on the Proactor loop.** Switching to the selector loop (which Jupyter, some frameworks, and some users' code does; e.g. Sanic, nicegui-under-reload, Streamlit/Jupyter users all hit `NotImplementedError` when using async subprocesses) makes subprocess creation fail with `NotImplementedError` for the async-subprocess machinery in *their* environment. [18][19][20][21]
- **Even on the Proactor loop, `asyncio.create_subprocess_exec()` historically worked *only in the main thread*** — the loop thread must be the main thread; running the loop in a background thread breaks the subprocess transport setup on Windows. This matters *directly* for any design where the sync wrapper runs the event loop in a bundled background thread and the async core creates subprocesses inside that loop. This was reported and tracked as bpo-35635 ("asyncio.create_subprocess_exec() only works in main thread"); flag: **verify whether any 3.12/3.13/3.14 change lifted this** — I did not find evidence that it has, and the marimo issue #9182 as well as Sanic/Streamlit threads from accumulation in the 2020s corroborate that it persists *at least* on combination setups until recently. [22][19][21]
- **The emuctl implication is stark:** if the sync wrapper spins up a background-loop portal on Windows and the async core issues `create_subprocess_exec` (adb/memuc) from that loop, Windows users of the *sync* surface may hit `NotImplementedError` — i.e., the sync facade on Windows is the risky combination, not the async core. (Synthesis from the prior bullet; treat as a headline risk to validate immediately with a 20-line repro before locking the bridge design.) *This finding changes, potentially, locked decision #1's runtime assumption, but not the decision itself.*

## 4. Recommendation for emuctl

**No locked decision should be revised.** Locked decision #1 ("async core + sync wrapper; sync bridge = highest-risk layer and prime test target") is confirmed as the right shape by the evidence — it matches what anyio itself, fastmcp, playwright, and the whole httpx/openai ecosystem recognize as a real design axis, not an afterthought. Locked decision #7 (Python 3.12+) is also right for this design: no Python-3.10-era `nest_asyncio` needed on the sync path. Two **sharpenings** and one **stay-open flag**:

1. **Bridge design (new decision to lock):** implement the sync wrapper over `anyio.from_thread.start_blocking_portal()` / `BlockingPortalProvider`-equivalent semantics: a per-instance (or lazily shared per-instance) event loop in a dedicated thread; sync methods = `portal.call(coro, ...)`. Reasons: (a) it *cannot deadlock* when a sync user calls it from a thread without a running loop and raises/works sanely when there *is* an ambient loop; (b) it keeps the async core pure-asyncio (no anyio in the core's public surface, preserving the zero-dep philosophy for the core; anyio becomes a *bridge-layer* dependency only — flag: check whether zero-dep-core philosophy tolerates anyio as a required dep or only under an extra like `emuctl[bridge]`; probably required, it's tiny and pure-Python).
   - **Do NOT use `asyncio.run()` per call** (new loop per call: kills perf, breaks ordering, leaks tasks) and **do NOT use nest_asyncio** (fragile monkey-patching, notorious conflicts). Detect a running loop on the calling thread (via `asyncio.get_running_loop()` / sniffio-like guard) and raise a single, designed `SyncCallInsideEventLoopError` with a message naming the escape hatch (`await client.x()`). This is the most important sharpening: any other default (or letting asyncio's message surface to the user) creates the #1 support burden documented across Jupyter/Sanic/Streamlit/NiceGUI [19][20][21][15].
2. **Sync-side cancellation must be documented as "cancel = abandon", not "abort"**, matching anyio's `abandon_on_cancel` reality [4]; use portal `Future.cancel` where it exists for partial progress, and document that per-instance close() (portal exit) is the real stop.
3. **Session/context-manager lifecycle:** sync-side context managers must go through `portal.wrap_async_context_manager(...)` so enter/exit happen *on the loop* with cancellation semantics intact — do not invent a parallel `__enter__/__exit__` implementation by hand. AnyIO ships the correct version. [4]
4. **Executor sizing:** pin/limit any `to_thread.run_sync` use inside the async core to a named capacity limiter, matching anyio's recommended style; default limiter's 40-thread cap is fine but we should set an emuctl-tuned cap so blast radius from a blocked vendor CLI is bounded, in the spirit of "bounded internal waits" (NOTES.md). Note explicitly that AnyIO's worker limiter is independent of asyncio's own ThreadPoolExecutor default size [4][16].
5. **Windows/threads for the sync wrapper — action now, before further design:** a 20-line repro harness that calls the sync facade on **Windows** while the async core creates an `asyncio.create_subprocess_exec` child, since subprocess-on-asyncio in a *non-main-thread* loop is a real, documented Windows constraint [22][19][21][18]. Options if it does fail (per design): (a) run the *child-creation* step on the calling thread (sync callers' main thread) and let the loop await its exit; (b) use async core's blocking subprocess fallback path only on Windows/multi-thread loops — but keep core pure-asyncio; (c) treat the creation-site as part of the bridge, not core. This is a **stay-open design decision** contingent on the repro, but the choice belongs in this artifact because it is *entirely* an async-core/sync-bridge seam issue, not a core issue.
6. **Contract to carry into the bridge's test plan (start here — see §5):** (a) portal reuse across ≥2 threads; (b) exception propagation identical to async twin; (c) cancellation leaves work running but returns; (d) terminating the portal mid-op; (e) wrapped context managers pair correctly with `exit()` raising.

**Stay open:** the decision of whether the async core is **pure-asyncio** or **anyio-abstracted backend-neutral** is not locked by DESIGN.md and should be. My recommendation from the evidence: **anyio only at the bridge; stay pure-asyncio in the core** (anyio's backend-neutral style pays only if emuctl ever wants trio/multi-backend support; our needs are asyncio-only in practice — CPython 3.12+ users overwhelmingly on asyncio, and anyio-trio compat would impose their boilerplate on our subprocess/ADB path; revisit only if a consumer asks for trio).

## 5. Open questions

- **Subprocess-on-asyncio-background-thread on Windows, 3.12/3.13/3.14, ground truth.** Verify directly with a minimal repro against bundled Python versions (Windows CI run once). Highest-priority open item before bridge implementation, per §4(5).
- **Whether the sync surface needs trio support** and whether that changes anyio-in-core. Given 2026 practitioner evidence, treat as "no unless a consumer requests it"; revisit at v1.0 planning.
- **Bridge-layer token cost of anyio for zero-dep core philosophy.** anyio as a required quick transaction beats writing our own portal (two days of edge-case work). Confirm at packaging review (interacts with artifact 03).
- **`unasync` as insurance** if the sync twin drift becomes a recurring maintenance tax. Revisit only in 6+ months with real drift data.
- **A `__del__`/atexit contract for the sync surface.** Finalizer must not own portal shutdown; explicit close() required. Determine at bridge implementation.
