## 1. python-semantic-release × static version in pyproject.toml / uv_build — CONFIRMED

- **Verdict: supported, first-class.** PSR's docs have a dedicated **"UV Project Setup"** guide (python-semantic-release.readthedocs.io → Configuration Guides → *UV Project Setup*, present in the 10.x docs tree as `configuration-guides/uv_integration.html`). It explicitly configures `version_toml = ["pyproject.toml:project.version"]` against `project.version = "0.0.0"` — exactly the Route D static-version shape artifact 01 chose. Getting-started docs show the same snippet.
- **Key naming nuance:** the correct key for TOML files is **`version_toml`**, not `version_variables`. `version_variables` is the regex find/replace variant for non-TOML (JSON/YAML/…) files. PSR's own pyproject.toml uses `version_toml = ["pyproject.toml:project.version"]`. Writing `version_variables = ["pyproject.toml:project.version"]` (the formulation in the prompt) is the wrong key for TOML — fix in artifact 07's mental model.
- **No uv_build incompatibility.** PSR only edits the pyproject text and runs `build_command`; the backend (`uv_build` vs hatchling) is opaque to it. The official UV guide's example `build_command` is literally `uv lock --upgrade-package "$PACKAGE_NAME"` + `uv build` (or `pip install -e '.[build]'` around it).
- **uv.lock is NOT updated automatically — it must be handled in `build_command`.** The UV guide states: bumping pyproject "will cause uv to fail on the next execution because the lock file will be out of sync with the project's definition file," and prescribes `uv lock --upgrade-package "$PACKAGE_NAME"; git add uv.lock` inside `build_command` (the `--upgrade-package` intent is *only* to restamp the project's own version in the lock, not to upgrade deps). This refines artifact 01's rec. 5 ("conventional-commit release chores should also update the lock when regenerating") — the mechanism is PSR's build_command, not a separate chore.
- **Impact on DESIGN.md:** none — locked #6 (conventional-commit auto-release + OIDC) survives fully; artifact 07's PSR recommendation is now doc-confirmed, with the caveat that the workflow must adopt the UV guide's build_command verbatim so `uv.lock` stays in sync and CI never hits a stale-lock `uv build` failure.

Sources: https://python-semantic-release.readthedocs.io/en/latest/configuration/configuration-guides/uv_integration.html ; https://python-semantic-release.readthedocs.io/en/latest/concepts/getting_started.html ; https://github.com/python-semantic-release/python-semantic-release/blob/master/pyproject.toml (v10.6.2 dogfooding `version_toml`); PSR docs v10.7.0 configuration page.

## 2. asyncio subprocess "main-thread limitation" in 3.12/3.13 — REFUTED (fixed long ago, predates 3.12)

- **Verdict: the limitation does not exist in 3.12/3.13 — it was fixed in Python 3.8 and never returned.** bpo-35635 ("asyncio.create_subprocess_exec() only works in main thread") was **closed as a duplicate of bpo-35621** and resolved by the **`ThreadedChildWatcher` switch in 3.8**: the 3.9–3.14 asyncio docs read "Changed in version 3.8: UNIX switched to use ThreadedChildWatcher for spawning subprocesses from different threads **without any limitation**."
- **Current CPython docs (asyncio-subprocess.html, fetched 2026-10, Python 3.14 doc snapshot — the section is unchanged for 3.12/3.13): "Standard asyncio event loop supports running subprocesses from different threads by default."** On Windows, `ProactorEventLoop` (default since 3.8) is the only loop with subprocess support; `SelectorEventLoop` has none. So a Proactor loop in a background thread can spawn subprocesses.
- **Remaining platform notes that DO still exist** (don't confuse with the thread issue): signal handling (`add_signal_handler`) requires the main thread; on Python ≥3.14 Proactor loops warn if not closed before GC (cpython#141262); `-0.13` note — subprocess *cancellation* had a race fixed in 3.13/3.14 via cpython#145541 (issue gh-103847, "fixed Mar 2026"). None of these block the thread pattern.
- **AnyIO:** its docs place **no subprocess veto on `start_blocking_portal`** — the blocking-party docs (threads.rst, api.rst: `start_blocking_portal(backend='asyncio', backend_options=...)`) treat subprocesses as ordinary async code run on the portal's loop. The only Proactor caveat anyio documents is on a different API: `anyio.wait_socket_readable` — *"does NOT work on Windows when using the asyncio backend with a proactor event loop (default on py3.8+)"* (anyio 3.x api.rst warning). I.e. avoid `wait_socket_readable` under Proactor (use pipe/socket alternatives); subprocesses via the portal are fine.
- **Impact on DESIGN.md:** none, positive — removes a phantom risk from the async-core + sync-wrapper plan (locked #1). Design inference for blackbox: an asyncio-sync bridge via `start_blocking_portal` can safely `await asyncio.create_subprocess_exec` (adb, memuc, HD-Adb.exe) on Windows Proactor inside the portal thread; 3.12+ floor is safely above the fix.

Sources: https://docs.python.org/3/library/asyncio-subprocess.html ("Subprocess and Threads"); https://bugs.python.org/issue35635 (dup of 35621); https://docs.python.org/3.9/library/asyncio-subprocess.html (3.8 changelog note); https://anyio.readthedocs.io/en/latest/threads.html + https://github.com/agronholm/anyio/blob/master/docs/threads.rst; https://github.com/python/cpython/issues/103847 and #145541 (cancellation fix, Mar 2026); https://github.com/python/cpython/issues/141262 (Windows 3.14-only loop-close warning).

## 3. gh-action-pypi-publish attestation defaults × uv build — CONFIRMED

- **Verdict: attestations (PEP 740, Sigstore keyless) are generated and uploaded *by default*** whenever the job runs under **Trusted Publishing** against PyPI or TestPyPI. The README's "Generating and uploading attestations" section states it is "on by default for all projects using Trusted Publishing"; disable with `attestations: false`. It remains gated to TP flows (not API-token uploads) — matches artifact 07 §A3 point 4.
- **`uv build` dists are fully compatible** as attestation subjects: the action has nothing to do with *building* distributions (an explicit non-goal); it signs/attests whatever sdist/wheel files are in `dist/` — pure-Python `uv_build` output is ordinary PEP 427/517 artifacts, no builder-specific condition exists. Attestations are tied to the workflow's OIDC identity, not the build backend.
- **`uv publish` still uploads-only**: generation inside uv remains open (astral-sh/uv#15618; the upload-later behavior landed in uv 0.9.12 as PR #16731 — confirmed in artifact 01). So the FastAPI-style split (artifact 01 rec. 6: build with `uv build`, publish with `pypa/gh-action-pypi-publish`) is the only fully-attesting pure-OIDC route as of Oct 2026.
- **Impact on DESIGN.md:** none — this validates locked #6's implementation path; artifact 07's publish-job wiring stands.

Sources: https://github.com/pypa/gh-action-pypi-publish#generating-and-uploading-attestations (README, `unstable/v1`/`release/v1`); https://github.com/astral-sh/uv/issues/15618.
