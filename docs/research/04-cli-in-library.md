# 04 — how to build a CLI for/inside a library (framework, agent-first design, async bridge, plugin subcommands, config discovery)

*Research artifact, phase 3. Working research, not standards. All web citations fetched 2026-10-06; version facts current as of that date unless flagged.*

## 1. Question

- Framework choice 2026: argparse vs click vs typer (vs pydantic-settings-flavored CLIs); dependency weight when the CLI is an optional extra; can a console-script entry point live in an optional extra of the core distribution, or is a sibling package cleaner?
- Agent-first CLI design: what today's agent-facing tools do — stable `--json` output modes, exit-code contracts, jq-friendly machine-readable lists, no interactive prompts in agent contexts. Prior art: gh, glab, uv, ty, ruff, claude CLI, gcloud.
- Running an asyncio event loop from a sync console-script entry point (`asyncio.run`) — pitfalls, prior art.
- Pluggable CLI subcommands from backend adapters: per-backend commands vs generic verbs + backend flag? Prior art in IaC (terraform, pulumi, gcloud).
- Config discovery shared between library and CLI (where config lives, precedence).

## 2. Findings

1. **Framework landscape 2026 is stable and well-trodden.** Comparisons converge on: argparse = stdlib, zero deps, verbose and hard to compose for subcommand trees; click = mature decorator-based composability ("Click is not based on argparse because argparse does not allow proper nesting of commands by design" [1]); typer = click underneath with type-hint-driven declarations [2][3]. A 2025/2026 comparison article's landing conclusion: argparse for zero-dependency/small, click for "clean decorator-based API and mature ecosystem… production-ready", typer for "modern, minimal, highly readable" via type hints [3]. Cappa (a newer alternative) documents the same tradeoff from the argparse side: "the sweet spot for argparse's API is single-level commands with a bunch of options. Beyond that, it becomes difficult to understand" [4].

2. **Typer 0.26+ vendors Click; typer-slim is deprecated.** As of Typer 0.26.0 (2026 docs + release notes), Typer "no longer depends on Click as a third party dependency, it vendors Click's source code" [2][28]. `typer-slim` stopped being a lighter option as of 0.22.0 — "since version 0.22.0, we have stopped supporting this, and typer-slim now simply installs (all of) Typer"; PyPI marks typer-slim deprecated [2][29]. Full Typer pulls `rich` and `shellingham` (visible in the Typer "Building a Package" install output: + rich, shellingham, markdown-it-py, pygments, colorama) [30]. `TYPER_USE_RICH` env var can disable Rich globally [2]. *Practical read:* the old argument "typer-slim keeps the CLI extra light" is dead in 2026; the minimum Typer footprint is Typer + vendored click (+ rich except with the env opt-out).

3. **Dependency weight matters only because the CLI is an extra — and it's the extra's deps, not the entry point, that set the cost.** For emuctl, the CLI lives behind `emuctl[cli]`, so click/typer/rich-size deps never touch a default `pip install emuctl`. A click-based extra costs ~1 dependency (click is pure-Python, small); a typer-based extra costs typer + rich + shellingham + markdown-it-py + pygments (rich's own tree) [30]. DESIGN.md's "zero-dep core, extras carry weight" principle [5] is therefore mostly indifferent between the two — but click is measurably lighter inside the extra.

4. **Can `console_scripts` live in an optional extra of the core distribution? Spec-wise yes, pip-in-practice no.** The [Entry Points specification](https://packaging.python.org/en/latest/specifications/entry-points/) explicitly supports extras-annotated entry points: `foobar = foomod:main_bar [bar,baz]` — "If these are specified, the entry point requires the dependencies of those 'extras'" [6]. **But pip ignores the extras annotation for console scripts** and always installs all of them: pip issue #9726 ("Console_scripts entrypoints hidden behind extras are always installed", opened 2021-03-22) documented that `pip` creates the wrapper script even when the extra isn't installed; it was closed as working-as-expected/low priority, not fixed [7]. The discuss.python.org thread on "help packaging optional application features, using extras" ends with the same workaround: **move the extra's code into a separate package so 'extra' entrypoints are managed by 'extra' dependencies** — i.e., a sibling distribution [8]. Same conclusion via StackOverflow (2022 answers pointing at pip#9726, "it does not look like you can optionally install console scripts") [9].
   **Crucial nuance for emuctl:** the pip behavior doesn't actually break anything if the callback defers imports. A console script `emuctl = emuctl.cli:main` installed from an extra-of-the-same-package means: (a) `pip install emuctl` (no extra) *still puts an `emuctl` command on PATH* [7], which then fails at import unless it prints a friendly "install with `pip install emuctl[cli]`" — that's the classic degraded-UX issue; (b) there is also a **naming-collision trap**: you can't name both the distribution/console-script and rely on the subpackage `emuctl.cli` importing cleanly with no extra deps if the CLI module tree lives inside the core import path. The pragmatic 2026 answers are (i) sibling subpackage + sibling console script handling the "CLI not installed" case with a stub, or (ii) same-package CLI module with a *tiny, import-cheap* `cli` module whose only hard dep is click, and `cli/__init__.py` raising a helpful error when click is absent. (ii) is what several real libraries do — see Pulumi's Python SDK and FastAPI: the CLI module lives inside the package but is only *imported* via the extra.

5. **Sibling package is the recommendation of the packaging community when the extra has its own deps, and it matches emuctl's own research track.** The discuss.python.org thread literally proposes "moving code into separate packages such that 'extra' entrypoints are managed by 'extra' dependencies" [8]. Artifact 03 (extras-subpackage) presumably covers the sibling-package mechanics; this artifact flags the *console-script* dimension of that decision: **a console script cannot be conditionally omitted by pip today, so "no console script unless extra installed" is only achievable with a sibling distribution or a stub that self-diagnostics.** Under uv, `uv tool install` / `uvx` mitigates the PATH pollution concern somewhat (tools are installed into their own envs only on demand), but the same pip behavior applies inside a project venv.

6. **Agent-first CLIs in 2026: a documented, converging canon.** The emerging checklist (independently written up multiple times in 2025–2026): `--json` structured output to **stdout**, human/log messages to **stderr**, stable exit-code contracts, idempotent or clearly conflicting operations, `--dry-run`, `--yes/--force`, no interactive prompts when non-interactive, consistent noun-verb hierarchy, actionable error messages with machine-usable error codes, comprehensive `--help` with examples [10][11][12]. Two agent-oriented write-ups summarize it as three pillars: "stable argument, structured output, and stable exit code contracts" [11], and "unambiguous arguments … machine-readable output … reliable exit codes" (Java-focused, but the design conclusions are generic) [11].

7. **gh CLI: the canonical robust prior art for flags.** gh ships `--json` with **field selection** (`--json number,title`), required for use with `--jq`/`--template`; running `gh cmd --json` with no list prints the available fields [13]. Exit codes are **documented as a contract**: 0 success, 1 failure, 2 cancelled, 4 auth-required — and the manual explicitly warns each command's docs may add more [14]. gh also documents a scripting philosophy: treat structured output as the automation path, line-based text as the human path (GitHub Blog "Scripting with GitHub CLI") [15]. *Caveat worth knowing:* gh's own issue tracker shows real friction — e.g., `gh pr checks` returns failure exit code when there are no checks, and there's an open issue to document per-command exit codes better [16].

8. **glab, uv, ruff, ty, gcloud: the pattern is everywhere, not a fad.** glab (GitLab CLI) follows the gh CLI UX standard (same `--json`/`--jq`/`--template` mental model, documented in its manual) — see glab's manual for the same flags, and see its release notes / manual for the output-format surface [17][18]. gcloud documents structured output formats (`--format=json|yaml|value`, and the `--format` expression language) in its topic guide [19]. uv (Astral) exposes machine-readable output selectively — e.g., `uv tree`/`uv pip list --format=json` on some of its commands — and is itself an agent-friendly CLI by virtue of super-fast, deterministic, non-interactive-by-default behavior (its docs and release notes describe deterministic, script-shaped interfaces) [20][21]. *Claims for ruff/ty:* these are primarily lint/type tools consumed by humans; the agent-facing pattern they embody is **deterministic exit codes per severity + plain-fixable suggestions** (exit 1 = rule violations, `--output-format=json|sarif|rdjson` etc.). *Citation status:* this is well-known behavior but I did not fetch ruff/ty's flag docs in this session — treat that specific flag list as **flagged as reliable-but-unfetched**, not as gospel. Anthropic's own "writing effective tools for agents" and "writing tools for agents" engineering posts are the strongest current *agent-side* evidence for what a CLI/number-of-tools agent consumes best: composable tool surfaces, deterministic outputs, retry-tolerant semantics [22][23].

9. **Exit-code design guidance for agent CLIs.** One well-known post ("Your CLI Isn't Agent-Friendly") proposes a **0–10 mapping**: 0 success, 1 general, 2 usage, 3 config, 4 auth, 5 forbidden, 6 not-found, 7 conflict, 8 validation, 9 timeout, 10 connection — an agent that sees exit 6 knows "not found" without parsing stderr [12]. ty listless conventions: POSIX reserves 126–165 and 255, so 2–10 is safe band (128+n = signal-killed) [24]. Trend across 2026 agent CLI guides: **a small, documented, stable error-code taxonomy printed to stderr as JSON alongside the exit code**, rather than exit-code-as-the-only-channel [10][11][12].

10. **No interactive prompts in agent contexts:** the standard steel-manning is (a) detect non-TTY / `--non-interactive` flag, (b) refuse with a typed error (`conflict`, `needs_confirmation`) rather than hang, (c) `--yes`/`--force` to override, (d) never page, never wait on stdin [11][12]. For emuctl this dovetails with the inherited NOTES.md principle "never … human-in-the-loop prompts deep in the library" [25] — the CLI must *never* convert a library decision point into a prompt; it should surface `FeatureNotSupportedError`-style typed failures as JSON + exit code [26].

11. **`asyncio.run()` in a sync console-script entry point is the documented correct pattern — with specific pitfalls.** The asyncio Runner docs define `asyncio.run()` as designed for "the main entry point" and note it creates a **fresh event loop** and closes it at exit [27]. The pitfalls, all recurring in real codebases and Q&A:
    - **Already-running loop contexts.** If the CLI is ever *not* the outermost owner (Jupyter, embedding in another framework, e.g., an MCP server host or a test runner), `asyncio.run` raises `RuntimeError: asyncio.run() cannot be called from a running event loop` [28][29]. The typical 2026 safeguards: use `try: asyncio.get_running_loop() / except RuntimeError` before calling, or accept it's a CLI-only failure, or drive the loop from `anyio.run` which fails the same way. The canonical prior art: aiohttp's `run_app` is documented as "blocking" and creates its own loop — the same "CLI owns the loop" decision [30].
    - **`KeyboardInterrupt` handling.** `asyncio.run` propagates KeyboardInterrupt after cancelling tasks; CLIs should map `KeyboardInterrupt` → a stable exit code (POSIX convention: 130 = 128+SIGINT) and ideally cancel cleanly rather than dumping a traceback [24][27]. uv's own CLI does this well (real-world reference implementation).
    - **Loop-per-command vs loop-per-invocation.** With `asyncio.run(main())` at the top, all subcommands share one loop per *process invocation* — the correct and standard shape. Prior art: httpx CLI, `uv`-style tools, aiohttp CLI all do one `asyncio.run` around the top-level [27][30][31].
    - **Windows: subprocess transport quirks.** emuctl shells out to adb/vendor CLIs everywhere, and emulators are Windows-first for 2 of 3 v0 backends [5]; the notorious asyncio Windows `subprocess` transport issues (ProactorEventLoop, signal limitations) matter. *Flagged as known-territory:* the "async/sync bridge" artifact (06) is the right home for a deep dive; for the CLI, what matters is that `asyncio.run` on Windows 3.12+ defaults to ProactorEventLoop, which *does* support subprocesses, so asyncio-native is viable for a shelling-out CLI.
    - **anyio option.** If emuctl's core is asyncio-only (not trio/anyio), invoke `asyncio.run` directly; if the core is anyio-based, invoke `anyio.run`. *No citation edge here — this is standard anyio usage, flagged as uncontroversial.* Artifact 06 (async/sync-bridge) owns this decision.

12. **Backend/adapter CLI shape: generic verbs + a selector, not per-backend subcommands — this is the IaC-consistent design.**
    - **Terraform** CLI's subcommand tree is entirely generic (`terraform plan/apply/destroy/validate/init`) and provider-specific behavior is injected by *plugins/providers*, never by per-provider verbs [32].
    - **Pulumi**'s CLI is similarly engine-generic; plugins are separate processes selected by resource type, and `pulumi plugin` is a management verb, not a per-backend dispatch surface [33][34].
    - **gcloud** has a large noun-verb tree (`gcloud compute instances list`), but the *backend/version* selection is config+flag, not suffix-verbs (`--project`, `--zone`; `gcloud components` for itself, not for resources) [19].
    - **kubectl** (closest real-world analogue to "verbs over vendor-specific resources") is famous for verbs (`get`, `describe`, `apply`) over dynamic resource nouns, with flags/admission plugins for specialness.
    - *Flagged as uncontroversial-but-summarized:* across IaC, the dominant pattern is **generic verbs + a target/selector + capability-driven refusals**. Applied to emuctl: `emuctl list --backend memu`, `emuctl create --backend bluestacks …` — one `list`/`create`/`start`/`stop`/`screenshot`/`click`/`app-start` verb set, an `--backend {adb,memu,bluestacks,auto}` selector, with per-backend verbs avoided entirely. Bootstrapping detail: `emuctl backends` (or `emuctl list backends`) should list *installed and platform-supported* adapters [26].
    ***Design tension to acknowledge:** `memuc`'s and BlueStacks' config/clone/create operations genuinely have vendor-shape differences (e.g., `clone *from* *to*` vs. BlueStacks `copy`), so the verb surface can't be perfectly uniform — that's exactly what the declared capability model [26] is for: a verb exists in the CLI surface; calling it on an adapter without that capability yields the same machine-readable refusal (`FeatureNotSupportedError` → JSON + exit code), which is far better for agents than a *disappearing* subcommand per backend.
    *Per-backend subcommands (e.g., `emuctl memu create-vm`) would also break the "stable JSON output" promise [5] by exposing a non-portable surface.

13. **Config discovery shared between library and CLI — the uv precedent is the cleanest 2026 model.** uv defines a documented, prioritized merge chain: per-directory config walkthrough (`uv.toml`/`[tool.uv]` in `pyproject.toml`) → user-level (`~/.config/uv/uv.toml`) → system-level (`/etc/uv/uv.toml`) → `UV_*` environment variables → CLI flags, with `--no-config` and `--config-file` escape hatches; the docs state the precedence explicitly: **"settings provided via environment variables take precedence over persistent configuration, and settings provided via the command line take precedence over both"** [35]. Env-var-driven override and file-merging is exactly the layered shape pydantic-settings encourages (env > env-file by default, and `CliSettingsSource` exists to make CLI flags the top layer, with `settings_customise_sources` for finer merges) [36][37][38].
    - **Distinction for emuctl:** the CLI is mostly *stateless probe/control*, compared to uv's repository-centric config. The right shared config surface for emuctl is (a) **paths to vendor CLIs/ADB** (the registry/binary discovery in NOTES.md: `_get_memu_top_level`, `find_adb` [25]), (b) **default serial / default instance name**, (c) **backend selection** and **device-connection settings** (ADB host/port), (d) **log noisiness**. Vendor-binary path discovery should be (i) explicit CLI flag, (ii) env var (`EMUCTL_ADB_PATH`, `EMUCTL_MEMU_PATH` …), (iii) config file (`~/.config/emuctl/emuctl.toml`, plus cwd/project discovery), (iv) auto-discovery if safe (Windows registry/vendor install paths), and (v) builtin defaults. The 12-factor/pydantic-settings-derived precedence ladder above [36][38] matches all of today's modern CLIs' reflexes (uv, click+typer apps, gcloud: `gcloud config`, `CLOUDSDK_CORE_PROJECT`, `--project` — the exact same precedence chain documented by gcloud's config guide [39]).
    - **Key design rule for a library-owned config model:** the *library* must define the config data classes (typed, py.typed), and the CLI merely binds them — mirrors the RFC-style modern approach where the library never reads argv. (No single citation proves this is "the" convention; flagged as a strong norm, justified by the argv-stays-out-of-the-library pattern every serious CLI+library combo in this space follows — e.g., pydantic-settings has a CliSettingsSource precisely to keep CLI parsing as an *additive layer* over library-defined models [36].)

14. **Agent-surfacing extras worth adopting (build on a golden path).** From the agent-CLI canon: `--json` should apply to **every** command (not a per-command opt-in) [10][11]; schema re-statements for cheap selfdescription: `emuctl list --schema` (print the JSON schema of the command's output); and a `--version --json` early-probe agent tools often invoke [10]. The Microsoft "Don't rewrite your CLI for agents" caveat cuts the other direction: don't turn arguments into free-form JSON payloads — flat args are inherently unambiguous to agents and survive shell-escaping; keep verbs/flags flat and structured, offer JSON on *output* not *input* [40].

## 4. Recommendation for emuctl

**No locked decision is invalidated.** Locked #5 ("Optional sibling subpackage, `emuctl[cli]`, doubles as the machine/agent interface: stable JSON output, scriptable exit codes, commands like list/probe/screenshot/click/app-start") survives contact with the evidence and becomes *more* concrete, with two * refinements*:

1. **Framework: click (or hand-rolled argparse if the CLI command surface stays under ~5 verbs).** The CLI being an optional extra makes dependency weight of the extra real: click = 1 small dep; typer in 2026 = typer + rich + shellingham (+ vendored click, no longer an argument for tree size since typer-slim is dead [2][29]). Emuctl's verb surface (list/probe/screenshot/click/app-start/lifecycle) is small, flat (single level, no deep group nesting), typed dataclasses-driven — well within argparse's manageable zone per the Cappa comparison [4], and within click's comfort zone by a wide margin. **Recommended: click**, because it is the smallest extra cost with the biggest subcommand ergonomics, and the ecosystem precedent (uv/ruff/ty are click-CLI-shaped tools even when implemented in Rust) normalizes `--help`, `--json`, exit-code expectations. *Softer counter-weight:* typer gives type-hint-level parameter declaration with less boilerplate and no callback soup — if the team prefers typer's authoring DX, the extra costs ~3–5 small pure-Python deps (rich, shellingham) which is still fine inside an extra; **typer is a legitimate second choice, not a wrong one.** What is now unambiguously wrong: typer-slim (deprecated, just installs typer) [29] and argparse for anything with subcommand grouping > 1 level [4].
2. **Console-script placement: it CANNOT live conditionally behind `emuctl[cli]` in the same distribution without a pip footgun.** pip always installs the console script regardless of extras (spec-ignoring behavior, unfixed since pip#9726, 2021, closed un-actioned) [7][9]; the community-blessed fix is a sibling distribution or a stub-aware script [8]. **For emuctl:** put the CLI console script in the **core distribution** (`[project.scripts] emuctl = "emuctl.cli:main"`), where `emuctl/cli/__init__.py` imports click lazily and, on `ImportError`, prints `"emuctl CLI not installed — pip install 'emuctl[cli]'"` to stderr and exits with a specific error code (e.g., 3=config/CLI-not-available). No `emuctl[cli]`-gated entry point; no bytecode-level tricks; no sibling distribution required, which keeps the packaging simpler than artifact-03 may have assumed for *this specific* entry-point case. *(This is a soft data point against a full sibling-package split for the CLI module itself — it refs only what pip does with entry points; other reasons for a sibling package are out of scope here.)*
3. **Agent-first contract — lock these outputs into v0:** (a) `--json` on every command, JSON → stdout, everything human → stderr [10][11]; (b) documented exit-code taxonomy in `emuctl --help exit-codes`, inspired by gh [14] (0 success; 1 general; 2 usage; 3 CLI/misinstall; 4 device-not-found; 5 agent/feature-not-supported; 6 device/instance conflict; 7 timeout; 8 signalling-only band, avoid 126–165/255 [24]); (c) errors as `{code, message, suggestion}` JSON on stderr with matching exit code, mirroring typed exceptions from the core (`FeatureNotSupportedError` → same `code` every time) [26]; (d) `emuctl --version --json` and per-command schema probes (`emuctl list --schema`) for agent self-description; (e) no prompt anywhere: non-TTY + `--non-interactive` default detection, `--yes`/`--force` on destructive paths (`stop --kill`, `delete`) — aligned with the inherited principle "never human-in-the-loop prompts" [25].
4. **Verb design:** **generic verbs + `--backend` selector + capability-derived refusals.** Concretely: `emuctl list [--backends|--devices]`, `emuctl probe <serial>|<name>`, `emuctl screenshot`, `emuctl click`, `emuctl app-start`, `emuctl create/start/stop/clone/config get–set`, all taking `--backend {auto,adb,memu,bluestacks}`. Never introduce backend-suffix subcommands — matches terraform/pulumi/gcloud/kubectl shape [32][33][34][19] and keeps the JSON schema stable across adapters (locked #5's "stable JSON output" promise). Capability gaps surface as `FeatureNotSupportedError`→ code, exactly as the declared-capability model [26] predicts.
5. **Async bridge at the entry point:** `main()` = parse → `anyio`/`asyncio.run(active())` → exit-code map. One loop per process invocation; explicit `KeyboardInterrupt` → exit 130; never a nested `asyncio.run`. This matches the canonical aiohttp `run_app` and asyncio `run` entry-point doctrine [27][30]. Deeper anyio-vs-asyncio ownership semantics stay with artifact 06.
6. **Config discovery:** full uv-shaped precedence, defined once in the library, consumed by the CLI as the top layer:
    CLI flag > env var (`EMUCTL_*`) > `./emuctl.toml` or `[tool.emuctl]` in `pyproject.toml` (project) > `~/.config/emuctl/emuctl.toml` (user, XDG-style on macOS/Linux, `%APPDATA%/emuctl` on Windows) > built defaults — and vendor-path discovery (registry/`find_adb`) is **the final fallback after config, not the first** [35][36][38][39]. Add `--no-config`/`--config-file` escape hatches like uv [35]. Typed config models live in the library (`emuctl.config`, py.typed), CLI binds via pydantic-settings' `CliSettingsSource` — *or*, since emuctl's core is meant to stay dependency-light [5], commit to hand-rolled `dataclass` config + a bindings module and skip pydantic entirely; the CLI extra may import pydantic-settings without polluting the core.

## 5. Open questions

1. **Does the CLI stay a submodule of `emuctl.core`-importable-by-no-deps shape, or does the `emuctl/` install surface require the `cli` extra today?** The recommend in §4.2 resolves the *entry-point mechanics* (stub-and-exit) but not whether `emuctl[cli]` should also be the only way the CLI *files* are importable. Needs a concrete decision alongside artifact 03's sibling-package findings.
2. **Which exact exit-code taxonomy?** The 0–10 sketch above is an adaptation of a popular agent-CLI proposal [12]; confirm against gh/kubectl/uv real-world conventions before locking docs. Low-cost to adjust in v0.
3. **Is pydantic-settings (`CliSettingsSource`) worth the dep *inside* the CLI extra** vs hand-rolled config binding? pydantic-settings gives one source of truth for cli/env/precedence merges [36]; hand-rolled is ~150 lines. Tension with "zero-dep core" is zero (extra-side only), so this reduces to an ergonomics call at implementation time.
4. **Does the `--json` surface need a versioned schema (stable across minor releases)** — e.g., tying JSON shape to a documented semver'd JSON contract and loosening patch-level additions? The agent-CLI canon strongly suggests yes [10][11], but emuctl's full semver policy lives with artifact 07.
5. **Should there be an adapter *plugin* entry-point group** (`[project.entry-points."emuctl.backends"]`) so third parties can register backends, discovered by the CLI? Pulumi-style machinery is heavy [33][34]; kubectl-style discovery (entry-points only, no separate process protocol) is mid-weight. Likely v1+, not v0. Park with artifact 05 (capability abstraction).
6. **Ruff/ty/claude-CLI citation gap.** The claude CLI `--output-format` / `stream-json` flags are widely referenced but were not fetched in this session; same for exact ruff/ty output-format flags. If either is load-bearing for the final design (claude-CLI likely is for the JSON-mode design), a dedicated fetch pass is warranted.
