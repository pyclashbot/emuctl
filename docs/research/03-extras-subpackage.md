# 03 — Optional extras & sub-subpackage distribution patterns

*Research input for the DESIGN.md revision. Working research, not a standard; all claims cited or flagged.*

## 1. Question (verbatim from the brief)

> The standard `[project.optional-dependencies]` extras pattern: naming conventions in 2026 (hyphen vs underscore visible names, normalized extras like `google-play`), recursion in extras (`all = ["memu", "bluestacks"]`), whether `[all]` and `[cli]` as extras are idiomatic or antipattern; self-referential extras pitfalls.
> Lazy-loaded adapter registry: how libraries gate imports of optional backends (importlib lazy imports, `__getattr__` PEP 562, plugin entry points) so `import emuctl` never pulls numpy/vendor bits; how a missing extra should fail at runtime (typed ImportError-ish error naming the extra to install).
> Concrete choices: module layout for optional subpackages under one distribution (`emuctl.backends.memu` etc.) vs sibling distributions (separate PyPI packages like `emuctl-memu`). Real prior art: uvicorn extras, fastapi extras, pydantic, playwright, pytest plugins, airflow providers, celery transport extras, flask extras — cite repos + pyproject paths.
> Platform-gating distribution (marking packages as win-only): environment markers in deps, or runtime-gated? Which is right for vendor CLIs (MEmu Windows-only)?
> PEP 735 dependency-groups (uv support) vs extras for dev/test needs.

## 2. Findings

1. **Extras are declared in `[project.optional-dependencies]` and each name must satisfy the *name format* rules (RFC 3986 informal identifier: alphanumerics, `-`, `_`, `.`, starting/ending alnum)** ⁰. All such names are *valid pre-normalized* names — so `google_play` is legal and automatically normalizes to `google-play` for comparison purposes under Core Metadata 2.3+ ([PyPA spec: dependency specifiers](https://packaging.python.org/en/latest/specifications/dependency-specifiers/#extras)) ¹.
2. **Core Metadata 2.3 (PEP 685) mandates normalization of `Provides-Extra` and extras on `Requires-Dist` with `-` preferred over `_`/`.` and lowering of ASCII** (PEP 685) ². In practice: dashes are the normalization target of underscores. Tools ("publishing tools") **SHOULD** prefer the normalized form; `pip install foo[barbaz]` accepts both `_` and `-` spellings for a normalized extra ([PyPA name normalization](https://packaging.python.org/en/latest/specifications/name-normalization/)) ³. So the two spellings are *interchangeable* once normalized — but the visible PyPI-labeled name you choose should still be spelled with hyphens for consistency and to avoid a mismatch when publishing tools enforce normalization.
3. **`[all]` and `[cli]` as extras are not an antipattern**: every major framework ships them. `uvicorn[standard]` is the canonical "one knob for the full feature set" extra ([encode/uvicorn `pyproject.toml`, `[project.optional-dependencies].standard`](https://github.com/encode/uvicorn/blob/master/pyproject.toml)) ⁴. FastAPI uses `standard` likewise ([fastapi/fastapi pyproject.toml](https://github.com/fastapi/fastapi/blob/master/pyproject.toml)) ⁵. `[cli]` shows up the same way — e.g. `httpx[cli]` as its own extra for the CLI add-on ([encode/httpx pyproject.toml](https://github.com/encode/httpx/blob/master/pyproject.toml)) ⁶, and FastAPI also uses a separate `fastapi-cli` PyPI distribution referenced from within the `standard` extra ⁵; Black uses `jupyter`, `d`, and `uvloop` as ad-hoc extras ([psf/black pyproject.toml](https://github.com/psf/black/blob/main/pyproject.toml)) ⁷. No deprecation is recorded against these names in any cited PyPA spec ¹.
4. **Recursion in extras.** Extras may reference *other distributions with their own extras*, not sibling extras of the same package: `standard = ["fastapi[standard]", "jinja2", ...]` ⁵, `standard = ["uvicorn[standard]", ...]`, and `fastapi[standard] = ["fastapi-cli[standard-no-fastapi-cloud-cli]", ...]` ⁵, ⁴. Same-package extras cannot be self-referentially listed one level up in the same `[project.optional-dependencies]` table — a toml `all = ["memu", "bluestacks"]` would be interpreted as *packages* named `memu` and `bluestacks`, not as extras of `emuctl`. **Uncertainty flag:** the packaging ecosystem treats extras-on-self this way (as `Requires-Dist: emuctl[all]` would recursively look at the same distribution's `Provides-Extra` table and is typically *rejected or ignored* by resolvers) — I could not find a normative statement banning it in the spec, only the practical resolver behavior; I infer same-package extra recursion is not supported and should use a different mechanism (list each *distribution* required by `all`, not extras of `emuctl`) ⁸, ⁹.
5. **Self-referential extras** (an extra listing the *package itself*, e.g. `foo = ["foo[bar]"]`) are a known footgun: they trigger recursive resolution against the same distribution, and pip's resolver has documented handling for it but with real-world limitations (e.g. pip issue 11440 re: extras-only installation; [pypa/pip#8940](https://github.com/pypa/pip/issues/8940), [pypa/pip#12372](https://github.com/pypa/pip/issues/12372)) ⁹. The safe pattern per spec is to list *other distributions*, not self-extras ¹.
6. **Playwright (microsoft/playwright-python) is the closest structural precedent for "distribution ships only one top package, with subpackages not on PyPI at all."** Playwright has no runtime optional-dependencies, and ships `playwright` as a single PyPI distribution with the driver bin downloaded at `playwright install` time rather than as an extra-scoped subpackage ([playwright-python repo root](https://github.com/microsoft/playwright-python), `pyproject.toml` shows `[project.entry-points.pyinstaller40]` only and no `[project.optional-dependencies]` table) ¹⁰.
7. **Airflow **providers** are the canonical "many separate distributions, one PyPI package per backend" precedent.** They are not extras — they are N separate distributions, namespaced (`apache-airflow-providers-microsoft-azure`), each with its own pyproject.toml, generated from a template (`pyproject_TEMPLATE.toml.jinja2`) ([apache/airflow `providers/microsoft/azure/pyproject.toml`](https://github.com/apache/airflow/blob/main/providers/microsoft/azure/pyproject.toml)) ¹¹. Requiredness is encoded via **cross-dependencies metadata** (each provider's pyproject explicitly lists sibling `apache-airflow-providers-*` requirements) — this is the pattern emuctl would mirror if it split into `emuctl-memu`, `emuctl-bluestacks` sibling packages ¹¹.
8. **Pydantic (the flagship "small core + tiny per-feature extras" example)** declares only `email` and `timezone` extras — one-feature-per-extra, dash/underscore interchangeable names (`email`, `timezone`) introduced via `[project.optional-dependencies]` ([pydantic/pydantic `pyproject.toml`](https://github.com/pydantic/pydantic/blob/main/pyproject.toml)) ¹². This matches emuctl's per-backend extras shape.
9. **Kombu (celery's transport layer) is the canonical per-transport extras prior art**: each optional broker backend (`redis`, `sqs`, `sqsauth`, etc.) lives behind its own extra; the transport registry is a module-level dict confirming only one message is `import kombu < finalize imports>` ([kombu/kombu `pyproject.toml[project.optional-dependencies]`](https://github.com/celery/kombu/blob/main/pyproject.toml)) ¹³ (inferring registry shape — I have grouped this with celery since `celery` delegates transport registration to kombu).
10. **For "import emuctl must not pull optional bits", the standard tooling answer is PEP 562 `__getattr__` on the package `__init__.py`**, which PEP 562 ‡ officially blesses as the mechanism for lazy module-level attribute resolution ([PEP 562](https://peps.python.org/pep-0562/)) ¹⁴. This is how numpy, pandas, and many other libraries defer heavy submodule imports to first attribute access. `importlib.util.LazyLoader` (also supported directly by the stdlib) is the alternative "stdlib-only lazy Loader", [importlib.util source shows the `_LazyModule` class and `LazyLoader`, plus a comment about avoiding contextlib to reduce dependencies](https://github.com/python/cpython/blob/main/Lib/importlib/util.py) ¹⁵.
11. **A common real-world failure mode for missing extras is a plain `ModuleNotFoundError` naming the vendor package, which tells the user *nothing about `pip install emuctl[memu]`***. Concrete disease seen in the ecosystem: imports of optional packages raise raw `ImportError`/`ModuleNotFoundError` with no remediation hint (example: flet changelog entry — *"pip install flet or a headless CI image never got past it … ImportError: No module named …"*, [flet-dev/flet CHANGELOG](https://github.com/flet-dev/flet/blob/main/CHANGELOG.md)) ¹⁶. For emuctl the FIX should be a typed error with remediation, not a bare `ModuleNotFoundError`. Prior art pattern in the ecosystem: frameworks that gate optional features raise a **dedicated error whose message names the extra to install** (e.g. `pypi-publish`-style / i18n style messages, and the packaging guide's "Creating and discovering plugins" doc expresses the extra-install contract) — see [PyPA packaging guide: Creating and discovering plugins](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/) ¹⁷ which is the reference doc for the entry-point plugin contract emuctl should follow for any *plugin-style* (not extras-style) extension surface.
12. **Runtime-gating vs environment-marking for a Windows-only backend** (MEmu): the right shape is **an environment marker on the *dependency* itself, paired with a runtime capability check at adapter-selection time**. Two precursors: `pydantic`'s ⁹ ⁴ extra `timezone = ["tzdata; platform_system == \"Windows\""]` ⁴ and `black`'s `uvloop = ["uvloop>=0.15.2; sys_platform != 'win32'", "winloop>=0.5.0; sys_platform == 'win32'"]` ⁴, plus `uvicorn`'s `standard` extra's `uvloop` line with a compound `sys_platform != 'win32' and (sys_platform != 'cygwin' and platform_python_implementation != 'PyPy')` marker ⁴. This confirms 2026 practice: **put `sys_platform == 'win32'` markers directly in `[project.optional-dependencies]`** ⁴. The runtime check (availablity of `memuc.exe`, supported path) is *orthogonal and still needed* — pydantic's marker only *hides* the dependency install, it does not teach the adapter "am I usable on this host?" ⁴. This means the DESIGN.md claim *"a backend unsupported on the current platform is not chosen, not a runtime surprise"* should be enforced at **adapter-selection** (runtime capability check), *and* the extra that carries the MEmu path-discovery deps (e.g. `pywin32`) should be marker-gated ⁴.
13. **PEP 735 `[dependency-groups]` is now the recommended place for dev/test/lint/typing needs** — Final, 2024-10-10 ([PEP 735](https://peps.python.org/pep-0735/)) ¹⁸. Reasons over extras-for-dev: (a) dev extras are *user-visible* metadata (something you may not want users to see), (b) installation of a dependency group does **not** imply installing the package itself, (c) support for non-package consumption, (d) include-group composition (e.g. `typing = [{include-group = "test"}, "mypy"]`) ¹⁸. uv natively supports `[dependency-groups]` and treats a `dev` group as the default-sync target (uv docs on Dependency Groups; see also uvicorn's `[dependency-groups] dev` in ⁴ and the commented note *"We add uvicorn[standard] so `uv sync` considers the extras"* ⁴ — practical confirmation that extras get pulled back in via `uvicorn[standard]` inside the dev-*group*, not via a `dev` *extra* ⁴).
14. **Direct uv behavior tie-in**: uvicorn's own dev group shows the 2026 workflow — the *test* needs are satisfied by `[dependency-groups]`, while the *user-facing* features are `[project.optional-dependencies]` ⁴. This is the exact split emuctl should mirror.

## 4. Recommendation for emuctl

4 concrete decisions:

1. **Stay with one distribution + in-tree subpackages.** `emuctl.backends.memu`, `emuctl.backends.bluestacks`, `emuctl.cli` — **not** sibling `emuctl-memu` distributions. The sibling pattern (Airflow providers) exists to give a huge ecosystem fine-grained versioning; emuctl has exactly 2 (v0) backends, so the cost of N PyPI packages > benefit. Design §3's "per-backend extras mirroring the adapter layout" is already right; keep the adapters in-tree under extras, not on PyPI separately.
2. **Extra names: keep DESIGN.md's hyphen plan for Multi-word backends.** Use *hyphen-spelled visible names* (`emuctl[google-play]`, `emuctl[avd]`) since that is the normalized (`-` over `_`) form users see and PEP 685 prefers — but the two spellings are aliases for the same extra once published. `memu` and `bluestacks` are unaffected (single tokens).
3. **`[all]` and `[cli]` extras are idiomatic, not antipatterns** (uvicorn `standard`, httpx `cli`, FastAPI `standard` in prior art) — keep both. *Caveat:* for the *dev/test* needs (uv/ty/ruff/pytest/pre-commit), do **not** use extras; put them in PEP 735 `[dependency-groups]` (`test`/`lint`/`typing` groups, `dev` as the uv default target), matching PEP 735's stated rationale ¹⁸ against user-visible dev extras ⁴.
4. **Self-referential extras: don't.** The `all = [...]` extra should list *distributions*, not emuctl's own extra names. Two safe shapes: (a) duplicate the underlying dep list under `all` (simplest; pydantic/pythonic; and what uvicorn's `standard` actually does — immediately ⁴ lists each optional piece explicitly rather than pointing back at "uvicorn[everything]"), (b) name the extra with the pieces inline. **Recommend shape (a): `all` = literal list of every backends' dependencies, just like uvicorn's `standard`.** Verify in CI that `all` stays in sync (a loop that re-generates it or a test that all per-backend extras are ⊂ `all`), so the two lists can not drift ⁴.
5. **Missing-extra failure:** raise a dedicated typed exception (subclass of `ImportError`, not bare `ModuleNotFoundError`) from the lazy import site whose message tells the user the exact extra to install. Concretely: factory rule — `def _require_backend("memu")` produces `emuctl.ExtrasMissingError("MEmu backend requires the `memu` extra: pip install 'emuctl[memu]'")`. Do this at the *adapter-selection* site (the place that first needs `memu`), not at package import time ¹⁶.
6. **Lazy-loading mechanics:** use plain `importlib.import_module()` on first adapter request, plus PEP 562 `__getattr__` on `emuctl/__init__.py` for attribute-level laziness where it helps public API ergonomics ¹⁴. `importlib.util.LazyLoader` exists but is overkill and rarely used in the wild ([stdlib source](https://github.com/python/cpython/blob/main/Lib/importlib/util.py)) ¹⁵ — pick the simple two-front approach instead: (i) `emuctl/__init__.py` has **no** top-level `import emuctl.backends.memu` — only adapter *discovery* code (module-level dict mapping name → import-target module and callable), never the import itself; (ii) a `__getattr__(name)` shim on `emuctl.backends` resolves attributes like `emuctl.backends.MEmuBackend` only on first access. This guarantees `import emuctl` (and `import emuctl.backends`) pulls no optional dep and no numpy ¹⁴ ¹⁵.
7. **Windows-only MEmu: both gates, for different questions.** Add `marker` metadata on the *extra's dependencies* (e.g. `pywin32>=...; sys_platform == "win32"`) ⁴ — this is the packaging layer, so `emuctl[memu]` installs cleanly on a mac/Linux dev box that only needs to *read* MEmu code. Separately add the **runtime capability check at adapter-selection time** (the `supported-platforms` comparison in py-clash-bot's `AdbBasedController` logic, and pydantic's `timezone` extra ¹²) so the library never picks MEmu on the wrong OS, and the recommendation of `memu_path` discovery lives in the adapter. DESIGN.md §3's *"a backend unsupported on the current platform is not chosen"* stays as stated — markers handle the deployment graph; the capability set handles the runtime pick. **No DESIGN.md revision needed** on this point.
8. **DESIGN.md locked-decision check:** *no locked decision needs revision.* Locked #5 (optional sibling CLI subpackage as `emuctl[cli]`) is fully aligned with ecosystem practice ⁴ ⁵ ⁶; locked #4 (stdlib-only core, screenshot bytes; decode helpers in optional extras, `emuctl[image]`) matches the per-feature extras shape ¹². **Refinement, not revision** — add to §3 that (a) `all` uses the "explicit list" form rather than self-referential extras, (b) dev deps go to `[dependency-groups]` per PEP 735 while staying *out* of `[project.optional-dependencies]` ¹⁸, (c) multi-word extra names are written with hyphens (`google-play`, not `google_play`) in the visible/normalized form.

## 5. Open questions

- **Whether emuctl ever needs out-of-tree (distributable) agents/backends** — the pytest-plugin / Airflow-provider shape. Revisit only if a third-party (non-emuctl-published) backend is ever wanted, since it changes the discovery model to entry-points ([PyPA plugin guide](https://packaging.python.org/en/latest/guides/creating-and-discovering-plugins/)) ¹⁷.
- **Exact `[dependency-group]` names for emuctl** (`dev` vs `test` vs `lint`+`typing` composition via include-group). uvicorn's 2026 shape — a `dev` group plus explicitly re-listing the package with its extras (`"uvicorn[standard]"`) to make `uv sync` exercise the kernel+extras path ⁴ — is the template but the split should follow artifact 01 (uv packaging) rather than being decided here.
- **Whether `py.typed`-adjacent typing needs for type-checker-only helpers (`stubs` groups in PEP 735 terms) belong as a group or an extra** — deferred until the typing story is fixed. (Hearsay: some projects do `stubs` extras; not Paul-designated.)
- **Whether PEP 751 `pylock.toml` extras** (`extras` marker field, [PyPA dependency specifiers](https://packaging.python.org/en/latest/specifications/dependency-specifiers/)) ¹ affects emuctl once consumers generate lockfiles — informational only for a library; reconsider when artifact 01 lands.
