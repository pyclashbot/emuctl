# 05 — Capability abstraction: prior art and patterns for vendor-capable device control

Artifact 05 of 07 · phase 3 research · written 2026-10-06 · informs DESIGN.md §2 (locked decision #3), §3 (platform gating), §6 deferred item 1.

## 1. Question

From DESIGN.md §6 and the research brief:

1. How do mature ecosystems express "this backend supports X" — Vulkan/OGL feature queries, Android API-level gating, Kubernetes, libgit2, Telegram MTProto layers, Terraform provider schemas, hardware drivers: static declared sets, runtime probes, or interface-with-default-vs-abstract?
2. IaC-style prior art the design flags (Pulumi, SST, Alchemy, Nitric): what patterns transfer to controlling emulators, and is declarative provisioning a natural extension of emuctl's `configure`/`create`?
3. What Python emulator/device-control prior art exists (adbutils, adb-shell, uiautomator2, Appium, Maestro, BlueStacks wrappers, pymemuc) and how do they structure multi-device/multi-emulator abstraction, lifecycle, and typing?
4. Protocol vs ABC with async methods; documented-defaults vs required-override; feature flags vs `NotImplementedError`; how SDKs degrade gracefully when a capability is version-dependent.
5. Is there precedent for a locked "one source of truth" capability set driving *both* introspection and call-time errors? Who does exactly this?

## 2. Findings

### 2.1 How mature ecosystems declare capability

**Vulkan — declarative booleans, queried, then enabled explicitly.** Vulkan reports support via `vkGetPhysicalDeviceFeatures`/`Features2`, a struct of `VkBool32` members where each value is "supported on this physical device" vs not [1][2]. The guidance workflow is *query first, then base decisions on the result*: the official guide frames device capability querying as the Vulkan developer's first responsibility [3]. Two structural details matter for emuctl:
- Features are *extension-scoped and additive*: "When new features are added in future versions or extensions, each extension should introduce one new feature structure" added via a `pNext` chain [2]. Capability sets are designed to grow without breaking the base struct — emuctl's capability set should likewise be additive, not a closed enum baked into v0 types.
- Support and *enablement* are separate axes: "fine-grained features … must be enabled at `VkDevice` creation time" after being queried [4]. A backend can be *capable* without a given session *using* it. This decoupling ("supported" vs "enabled") is useful for emuctl features whose use is per-call optional (screenshot format, GPS injection).
- Separately, Vulkan carries *limits* (queried numeric characteristics) apart from boolean features [3] — the same split applies to emulators (features vs knobs like RAM caps, resolution).

**Android itself — two distinct capability mechanisms.** On the device side: `ro.build.version.sdk` via `adb shell getprop` gates API-level behavior, and `adb shell pm list features` *enumerates hardware/system features* by name at runtime [5][6]. On the AVD side: hardware capabilities are *declared in the AVD config* (hardware profile + config.ini: camera, keyboard, sensors — a static declaration of what this virtual device has) [7]. Android's own Emulator gRPC service returns `FAILED_PRECONDITION` (code 9) at call time when "the AVD does not support hw-control" — call-time, per-capability errors from a distinct probe-enriched surface [8]. So Android itself uses **static declaration (AVD config) + runtime probe (`getprop`, `pm list features`, `avd status`) + call-time typed error (gRPC status codes)** in the same product. That triangulates exactly the shape DESIGN.md locked.

**Chromium/Blink — declarative data file, generated accessors, per-platform gating.** All runtime features live in one JSON5 file (`runtime_enabled_features.json5`) with `status` values (stable/experimental/test) and *per-platform keys* (Android, Win, Mac, Linux, iOS…) plus `implied_by`/`depends_on` relationships; accessors are generated from that one file, which is explicitly the "single source" ("Add your feature's flag … and the rest will be generated for you automatically") [9][10]. Take-aways: (a) features as a *single declarative data file* beats hand-written per-method checks; (b) per-platform status is first-class — precisely DESIGN.md §3's "platform support declared per adapter"; (c) `implied_by`/`depends_on` show why features benefit from *relationships* (a `bluestacks` feature may depend on `adb`), not flat independent booleans.

**Kubernetes — conditions, not booleans, for evolving capability.** Kubernetes expresses operational capability as status `Condition` objects (e.g. PDB's `DisruptionAllowed`) with enumerated, documented reasons (`SyncFailed`, `InsufficientPods`, `SufficientPods`) — "additional reasons could be added in the future" [11]. The API-conventions spirit: key/value facts that clients can reason about mechanically, with unknown-reason tolerance. This is the model *for* "machine-readable, extensible errors": `FeatureNotSupportedError` should carry machine-readable `feature`/`reason` payload fields, mirroring the documented extensibility of condition `reason` values [11].

**libgit2 — the closest direct precedent for the locked pattern.** libgit2 exposes `git_libgit2_features()` returning a *flag set* ("Query compile time options for libgit2", e.g. `GIT_FEATURE_THREADS`, `GIT_FEATURE_HTTPS`, `GIT_FEATURE_SSH`, `GIT_FEATURE_SHA256`), *plus* `git_libgit2_feature_backend(feature)` which resolves which backend (openssl-dynamic, mbedTLS…) *provides* an otherwise-boolean capability, and which returns `NULL` when the feature isn't supported [12][13]. This is: (a) one static feature flag set as the introspection surface; (b) multiple *providers/backs* for the same logical feature — i.e. true vendor pluggability with capability declared by provider; (c) graceful degradation at call time by checking before calling, not by scattered raises. libgit2 is exactly "several backends can compile out; features are declared per compilation and queryable at runtime." Note the maturity dimension too, from the changelog: SHA256 recently *graduated from "experimental" to "supported"* status, announced in the v1.9 changelog and v2.0 discussions [14] — *capability status values themselves evolve*, adding maturity levels beyond booleans.

**SSH — protocol-level capability negotiation with graceful degradation.** RFC 8308 (SSH "Extension Negotiation") defines the pattern: peers advertise extension support via an indicator in the initial `KEXINIT` list, then exchange a typed `SSH_MSG_EXT_INFO` message enumerating supported extensions (e.g. `server-sig-algs` so a client can avoid trial-and-error authentication penalties) [15]. Key principle: *capability discovery must avoid trial-and-error* — the RFC justifies itself by the cost of guessing ("to avoid trial and error as well as authentication penalties, a client must be able to discover…") [15]. Emuctl's analogous win: a caller checks `has_feature("clone")` instead of try/except.

**Telegram MTProto — capability as negotiated layer number.** A "layer" is the full set of supported constructors; the client opens with `invoke_with_layer(N)`, and the *server* responds appropriately to anything it knows about it. Since the schema changes per layer, each layer corresponds to a full *schema version* and each layer is documented in a per-layer changelog; an aggregated machine-readable index (`/api/config.json`) exposes the current layer + constants [16][17]. Telethon documents it plainly: "The different layers let Telegram know what a client is capable of" [18]. The pattern: capability = (schema version, per-version changelog, machine-readable index). Emuctl analogues: *adapter version* should be introspectable and features documented per adapter version, not just per package version.

**Terraform/Pulumi provider schemas — the capability surface is machine-readable.** A Pulumi provider literally ships a schema (JSON); the engine calls `GetSchema` via gRPC and the whole ecosystem (docs, codegen, policy packs, parameterization) keys off that machine-readable declaration [19][20]. Parameterization additionally means **a provider's schema, i.e. its capability surface, can be replaced or extended after the fact** via `Parameterize` — "a Parameterize call may change the set of resources and functions that a provider offers (that is, its schema)" [20].

**Hardware drivers — caps struct committed at probe time.** The canonical hardware-abstraction pattern is: an immutable caps struct returned once after construction/probe, never re-derived at call time; consumers validate against it before calling, and calling an unsupported feature is a typed validation error, not undefined behavior. (Flag: this paragraph is the author's generalization across GPU/web-platform capability APIs rather than a single citable source — the weakest-cited claim in this doc; it reproduces the Vulkan shape exactly and is included as a confirming pattern, not new evidence.)

### 2.2 IaC-style abstraction prior art (Pulumi / SST / Alchemy / Nitric)

**Pulumi.** Three relevant separations:
- *Provider = schema + CRUD executable*, separated from the *SDK* consumers import [21]. Backends stay replaceable because nothing downstream imports the backend internals — the schema is the contract.
- *Dynamic providers*: only `create` is required on the resource-provider interface; `check`, `diff`, `read`, `update`, `delete` are optional with default no-op behavior; the docs warn "A dynamic provider is often not the best tool for the job" when abstraction should instead be a *component* [22][23]. Lesson for emuctl's port shape: keep the *required*-override set minimal — but unlike Pulumi, back unsupported optional behavior with the declared capability set and a derived error, not a silent default (DESIGN.md #3 explicitly rules out silent no-ops).
- *Components are the higher-level abstraction layer*, explicitly the recommended answer for "grouping resources into a reusable abstraction," and they free consumers from per-vendor mechanics [21][24].

**Nitric.** Declares portable resources (bucket, api, queue) in app code; **deployment** to any cloud is a *pluggable provider* (AWS/GCP/Azure, Pulumi or Terraform backed); the docs are unusually honest about the gap structure: "Some services are unique enough that abstraction would be a disservice. Nitric aims to make common 'table stakes' services easy to use, but we never want to limit you" [25]; the per-provider capacity table shows **"Coming soon"/"Not implemented" entries live in the docs as first-class** (e.g. Azure Batch "Coming soon", Websockets "Not implemented" on Azure) [26]. *Nitric is the closest IaC analogue for emuctl's gap-handling honesty* — an emulator backend that cannot clone is exactly a "Not implemented" cell, and the mature pattern is to *declare* that in the feature table (and surface via the CLI), not to hide it.

**SST — component-per-outcome, transform escape hatch.** SST's model: built-in `sst.aws.*` components (Function, Bucket, Nextjs) constructed by outcome rather than vendor resource, backed internally by Pulumi providers, with a `transform` prop as an *escape hatch to the low-level resource args* [27][24]. The escape hatch is notable: a good abstraction anticipates that users sometimes need the raw vendor surface — for emuctl this suggests exposing a scoped, documented `adapter.vendor_passthrough()` (the pymemuc lesson: `send_adb_command_vm` exists and is needed) *rather than* trying to express every vendor knob in the typed surface.

**Alchemy — "Infrastructure as Effects," provider = wire-up checked by the type system.** Alchemy (TypeScript IaC on Effect) defines a provider as four lifecycle operations (read → diff to plan; reconcile, delete to apply), registered as Effect *Layers*; forgetting to provide `Cloudflare.providers()` while using a Cloudflare R2Bucket is a **type error caught at authoring time**, and adding a new cloud is "declare a type, implement a Layer" [28][29]. The transferable idea: *capability enforcement checked early, at wiring/construction time*, not deep into call flow — emuctl's analogue is the platform/selection gate resolving at adapter-choice time (DESIGN.md §3: an unsupported adapter is *not chosen*, never a runtime surprise), rather than erroring at first invocation.

**Does declarative provisioning transfer? State-engine semantics ≠ control semantics.** All four converge on one architecture: *declarative resource graph* + *pluggable deployment provider* + *state tracking* (Pulumi snapshots, Alchemy local state files, Nitric provider-managed state, SST via Pulumi) [22][25][28]. A state engine's value is *drift detection and plan/apply diffing against persisted state*. Emuctl's `configure`/`create` are **imperative lifecycle operations on pre-existing vendor-managed state** (registry entries, bluestacks.conf, MEmu's own VM store), where the engine (MEmu Console, Multi-Instance Manager) is the real authority over changes. Standing up a local state store to model that as plan/apply would duplicate MEmu/BlueStacks's own job — the opposite of emuctl's "treat emulator as black box, verify state, never second-guess engine ownership" principle in DESIGN.md §7. Nitric even shows the cost: its AWS provider got stateful import *eventually* — "Currently, the AWS standard provider supports importing both buckets and secrets… Importing resources via other providers is not yet supported" [30] — i.e. **declarative reconciliation was a lagging extension, not a day-one design**, which proves it can be added later without tainting the port surface.
- What *does* transfer without the state engine: (a) capabilities declared per provider, surfaced in machine-readable introspection (Pulumi GetSchema ↔ emuctl CLI `probe`); (b) components-as-outcome (SST) ↔ `Machine`/`Controller` façade typed at a goal level; (c) declarative *descriptors* (a `MachineSpec`/`AvdDescriptor` dataclass passed to functions like create/configure) without any "engine imposed diff/apply expectation." The safer v0 shape: **declarative arguments to imperative operations**, which is declarative-shaped without IaC semantics, and requires no persisted state on the host machine.

Design conclusion: declarative provisioning is *not* a natural v0 extension of `configure`/`create` — DESIGN.md's non-goal holds. The transferable pieces (capability surface, declarative *arguments*, outcome-shaped façade, honest per-provider gap tables) are cheap and apply directly.

Cross-cutting: **none of these projects resolves the port/adapter shape with typed capability declarations.** The mature shape in industry (Maestro, appium-uiautomator2-driver) is a flat port with one driver file per vendor, with capability documentation kept in a separate markdown table rather than surfaced as an API-level type. emuctl's locked decision #3 aims *above* all of these, which is consistent with emuctl's positioning (DESIGN.md §1) — no prior art we found does agent-facing capability introspection as an API surface, so it's a contribution, not a catch-up.

### 2.4 Protocol/ABC, defaults, graceful degradation

- **Protocol vs ABC.** PEP 544 Protocols are static-checking constructs by default; `@runtime_checkable` `isinstance()` "only checks that the relevant methods exist on the class… doesn't check for argument count, names, type hints," and the spec warns checks are unreliable and "can also be surprisingly slow" [48][49][50]. Core-team discussion confirms runtime protocol checks are intentionally weaker than the nominal checks they sit beside [51]. **Implication:** emuctl's port is *behavioral* (a shared ADB base layer implements most of the port; a strict nominal contract catches incomplete adapters at type-check time), so a **nominal ABC** matches py-clash-bot's model (`BaseEmulatorController` already is one) and gives all adapters a common base for `FeatureNotSupportedError` marshalling, vs structural `hasattr` checks. The spec also notes a protocol *can* be explicitly subclassed to inherit defaults, but that is a fringe use ("If a class is assignable to a protocol but the protocol is not included in the MRO…"), and PEP 544's ABC-flavored alternative already covers the case ("extensive use of ABCs might impose additional runtime costs" — not a concern at this adapter count) [48][50]. **Recommendation: ABC, not Protocol, for the port** — py-clash-bot already models it that way [52]. A `Protocol` remains right for *consumer-supplied callbacks* (e.g. an optional screenshot-transform hook) where `AdbBasedController`-style shared code doesn't apply.
- **Graceful degradation: the working grades.** Three real strategies, seen across the survey: *pre-flight* (Appium validates desired capabilities at session start; the consumer opts in via `appium:`-prefixed caps, and the backend refuses the whole session rather than failing one call) [37][39]; *fail-at-call* (Vulkan's per-capability `FAILED_PRECONDITION` on `getBrightness` when the AVD does not support hw-control [8]; Kubernetes condition reasons as typed failure facts [11]); and *optional-interface defaults* (Pulumi dynamic providers: only `create` required, `check`/`diff`/`read`/`update`/`delete` fall back to no-op [22][23]). Different products hit the same tension differently: **pre-flight (Appium), fail-at-call (Vulkan, K8s), silent no-op (Pulumi dynamic-provider defaults)**. DESIGN.md's rule ("never hand-written raises per method, never silent no-ops") selects fail-at-call + pre-flight introspection — *the silent no-op is the one anti-pattern among these*.
- **Version-dependent degradation via capability status + `depends_on`.** libgit2 graduated SHA256 from "experimental" to "supported" and resolves per-feature backends [13][14]; Chromium tracks feature relationships (`implied_by`/`depends_on`) in the data file itself [9]. The gray areas in emuctl's domain are concrete: BlueStacks version differences, and capabilities that exist on paper but do not work (py-clash-bot's `install_apk` is promised by the base contract yet raises `NotImplementedError` in two backends, `memu.py:1427-1431`, `google_play.py:463-467` [52]). That argues for adapters declaring features with an optional **maturity status**, not just presence/absence — bool-only models cannot express "promised-but-broken," which is precisely the failure py-clash-bot shipped.

### 2.5 Precedent for "one source of truth" driving introspection AND call-time errors

Named instances of exactly the locked emuctl shape:
1. **Chromium Blink** — one `runtime_enabled_features.json5` data declaration where "accessors are generated automatically" so *the same file* drives both static introspection of features and generated per-feature code sites [9][10]. This is the closest industrial precedent. (Note: its *output* is code generation, not runtime dispatch — the single-source property, not the generation, is what transfers.)
2. **libgit2** — `git_libgit2_features()` returns the same flag set used for consumer introspection, and its build system uses the same feature definitions to decide what compiles in — feature absence is the same fact driving both what callers can query and what the library can do at call time [12][13].
3. **Kubernetes conditions** — one machine-readable status model per condition type, driving "kubectl wait" automation *and* reason-flow errors from the controller [11].
4. **Terraform/Pulumi provider schemas** — the single schema JSON drives validation, codegen, docs, and error surfacing [19][20].
Conversely, no major industrial Python library we found pairs a runtime `features` property *and* typed call-time membership checks where both hit the same set without hand-sync. That is the gap emuctl's locked decision #3 is targeting; the important related precedent is that *capability declarations for SDKs which have done this* are shape-consistent (frozensets or dataclass of flags at adapter init).

## 4. Recommendation for emuctl

**Locked decisions this research validates (no revision):**
- **#3 (declared capability set + derived `FeatureNotSupportedError`) — keep, and the evidence is strong.** Vulkan, libgit2, Chromium, and Kubernetes all reach capability intent through a declarative, single-source artifact; DESIGN.md's rule ("never silent no-ops") exactly matches the one ranked anti-pattern found in the survey (Pulumi dynamic-provider implicit no-ops). Concrete shape to adopt: (1) a **capability `Flag`-style enum, stored as a `frozenset`** per adapter class (`FEATURES: frozenset[CapabilityFlag]`), documented per adapter and version; (2) a single call-time enforcement helper shared by all adapters, `def _require(self, flag: CapabilityFlag) -> None` raising `FeatureNotSupportedError(feature=flag, backend=…)`; (3) **relations between flags declared in the model** (`implied_by`/`depends_on`, copied from Blink [9]) so e.g. `clone` depends on `adb`; (4) surface the same set through the CLI `probe` interface and docs (the Appium `capability-sets.md` docfile pattern [39]). Keep the declaration as a plain typed Python literal in the adapter class body (the Chromium `json5` pattern transposed, without code generation).
- **Platform gating = the same capability mechanism** (DESIGN.md §3 already says this): the Blink per-platform `status` keys [9] are its precedent. Should surface in one place — e.g. adapter-level class attr `supported_platforms: frozenset[Platform]`, and a *probed* one placed next to it (Windows-only MEmu ends up "Not chosen, not a runtime surprise"). The bare Windows check that pymemuc/py-clash-bot do inline [52] becomes one declared dict key.
- **#1 (async core, sync wrapper) gains an independent domain validator:** `async-uiautomator2` already does *this exact job* with `to_thread` bridging, `device_factory=` fake-backend injection, per-(serial, port) lock, and exception after-release cleanup of device state [34]. Corroborating DESIGN.md's plan precisely.
- **Non-goal on IaC — keep.** Research's conclusion: **declarative provisioning is not a natural extension of `configure`/`create`**. What transfers without IaC is *declarative argument objects* passed to those imperative methods (a `MachineSpec`/`AvdDescriptor` dataclass passed to `create()`/`configure()`), after the Nitric-style pattern of "declare in code, provider applies" — but deliberately *without* Nitric's second half, a persisted state engine with plan/apply, which would reinvent state ownership that MEmu/BlueStacks already have. If a declarative-provisioning layer was later wanted, the pattern would be a new extension (an "instance-spec" flavor), not a revision of the core port; the state-engine's biggest *absorbed* cost is how it interacts with `restart()`-as-boot-primitive and py-clash-bot's imperative worker loop. See §5.
- **Port = ABC, not Protocol** — for all the reasons in §2.4. With ~4–6 adapters (py-clash-bot has 4 today), nominal checks beat structural `hasattr`-style checks [48][49][51], and the ABC matches py-clash-bot's existing `BaseEmulatorController`/`AdbBasedController` nominal shape — which is also how DESIGN.md §4 achieves "interaction primitives come free" (base-class shared implementations). Minimal required-override surface: `discover`, `router or launch-config`, `launch`/`stop` mechanics, and capability declaration — matching Pulumi's "only `create` required" lesson [22] without their silent-default trade-off (DESIGN.md rules out no-op default by lock).

**What to revise or research further:**
- **Add "declared vs probed" to the capability vocabulary** at DESIGN.md's next revision cycle. Capability surfaces are not only declared: Android itself distinguishes hardware an AVD *claims* (config.ini) from what the running OS *reports* (`getprop`, `pm list features`) [5][6][7]. Concretely: keep `features` 100% declared (machine-readable, no I/O), **but** allow each backend to optionally expose a second, cheaply-probed set (e.g. from `pm list features`) in a separate property — keeping introspection deterministic and cheap, consistent with DESIGN.md §7's bounded-waits rule. Exactly which probe keys are worth consuming is an implementation-phase question. [Flag: unproven here.]
- **Take the icapps sub-controller idea as a plan rather than a locked decision:** if the flat port grows to 20+ methods, the grouping pattern (`emulator.getPowerControl()`, i.e. capability-area sub-controllers) is a working Kotlin precedent [47] in-domain. Not a v0 need.
- **Cap maturity status beyond bool.** libgit2's "experimental-to-supported" graduation is documented in-tree [14], and the need is concretely present in py-clash-bot (`install_apk` promised by the base contract yet raising `NotImplementedError` in two backends [52]). Either: a capability record carries an optional maturity status (`experimental`/`supported`) — or keep plain booleans plus an explicit per-adapter TODO note. Lean toward the former.
- **Escape hatch on the port surface**, not in the adapter body. py-clash-bot's `send_adb_command_vm` exists because raw passthrough is *needed* [52]; SST's `transform` escape hatch [27] and pymemuc's `adb`-passthrough-style method [46] are the industrial pattern. A typed `vendor_passthrough()` (or per-backend specific path) with a docstring constraint ("no control-flow parsing of output") complements, rather than fights, the locked "never parse vendor stdout for control flow" rule (DESIGN.md §7).

**Concrete port shape (synthesizing the found patterns):**

```python
class CapabilityFlag(enum.Enum):               # grows additively (Vulkan pNext-chain style)
    SCREENSHOT, CLICK, CLONE, CONFIGURE, ...   # each member documented once, at the enum itself

@dataclass(frozen=True)
class FeatureSupport:
    flags: frozenset[CapabilityFlag]
    depends_on: Mapping[CapabilityFlag, frozenset[CapabilityFlag]]
    mature: frozenset[CapabilityFlag] = frozenset()   # members not yet "supported" graduation-eligible

class EmulatorBackend(abc.ABC):
    # declared introspection — set in each adapter's class body, no I/O
    features: frozenset[CapabilityFlag]
    supported_platforms: frozenset[Platform]
    # minimal required-override surface (the Pulumi dynamic-provider lesson, minus silent defaults)
    @abstractmethod
    def discover(self) -> ...:                 # cheap, discovery only (NOTES.md §7)
    @abstractmethod
    def restart(self) -> ...:                  # the explicit boot primitive (DESIGN.md §7)
    def _require(self, flag: CapabilityFlag) -> None:
        if flag not in self.features:          # call-time failure — the SAME set drives introspection
            raise FeatureNotSupportedError(flag, backend=self)
    # interaction primitives (click/swipe/screenshot/app-lifecycle) live in the
    # shared ADB base layer, implemented once — per DESIGN.md §4
```

## 5. Open questions

- **Runtime probe cost.** Nothing in this survey answered whether cheap probe calls (`adb shell pm list features`, `gsm status`) are worth the extra set (§4) over pure declared — this touches DESIGN.md §7's fail-fast "bounded internal waits" budget. Revisit when the ADB base layer is written.
- **Where does the call-time check live — a decorative hook baked into ABC dispatch, or explicit `_require()` at method heads?** Implicit dispatch hooks are hard for type-checkers (ty/mypy) to see and for the CLI to introspect; explicit `_require()` costs a one-line call per gated method but is honest, typeable, and is *not* the "hand-written raise" DESIGN.md #3 forbids (it derives from the declared set). Phase-3 implementation should test which shape ty validates cleanly. (Related artifact: `06-async-sync-bridge.md` should verify the sync wrapper re-raises `FeatureNotSupportedError` cleanly across the bridge.)
- **Per-version capability status graduation.** libgit2 *evolves* its feature set between releases (SHA256: experimental → supported) [14]; emuctl's backends may differ by installed vendor version (e.g. BlueStacks 5 minor versions) in `clone`/`copy` capability. Defer any mechanism until the "maturity status" idea has a real consumer.
- **Declarative provisioning at scale.** If a bigger consumer ever wants per-VM *declarative* state (multi-fleet py-clash-bot-alike with 30 instances), Nitric's pattern (declare in code, provider applies) would need a persisted state engine. That's a plan-level, not design-level, question; revisit only after real demand. (DESIGN.md §6 deferred item 1 is answered here in the design's favor.)
- **Copy specifics of the `capability-sets.md` docfile pattern** [39] to our repo: what exact table does an adapter-specific capability doc take? Defer to docs-work in phase 3.
